# 카피라이팅 작업 지침

브랜드 카피(슬로건·매니페스토·영업 카피)를 쓰고 검토하는 원칙과 순서.
`brandlogy_lint.py`가 코드로 잡는 것은 게이트에 맡기고, 이 문서는 코드가 못 잡는 판단을 다룬다.

---

## 1. 톤 원칙 (모든 작업 공통)

**지킬 것**

- 본론 직진. 군더더기, 과한 사과, 서두 인사를 뺀다.
- 구체적으로. 추상어 대신 사례·숫자·고유명사로 푼다.
- 진단을 길게 늘어놓지 말고 실행 가능한 다음 액션을 먼저 준다.
- 결론을 먼저, 근거를 뒤에 (역피라미드).

**쓰지 말 것**

- "솔직히", "사실은", "근본적으로" 같은 군더더기 부사
- "이 부분이 정말 중요한데" 같은 메타 표현
- 부정 긍정 대구("A가 아니라 B입니다")의 연속. 한두 번 강조는 괜찮지만 세 곳 넘게
  반복되면 AI가 쓴 티가 난다.
- 번역체. "가장 ~한 것 중 하나", "~을 가지고 있다", "~되어지다", "~에 있어서"

---

## 2. 카피워싱 금지 (가장 자주 사고 나는 지점)

**기존 카피·제안서 검토 요청은 새 글 수준 재작성이다.**

단어 한두 개를 다듬는 것은 검토를 안 한 것이다. 원본을 존중하거나 보존할 이유가 없다.
슬로건·매니페스토뿐 아니라 그 앞뒤를 꾸미는 모든 글(소개·설명·연결문장·캡션)을
브리프에 맞춰 처음부터 다시 쓴다. 명백한 오류만 고치고 끝내면 틀린 검수다.

제출 전 다섯 질문을 통과한다.

1. **두 축으로 풀었는가** : 브리프 자산 + 고객사 자체 설득. 한 축만 풀면 카피워싱이다.
2. **전부 다 봤는가** : 첨부된 자료의 전 페이지·전 슬라이드를 추출해 확인했는가.
3. **풀문장으로 정리했는가** : 디자이너가 그대로 복사해 쓸 완성 문장인가. 토막 단어는 안 된다.
4. **위치 지시를 붙였는가** : 그래프·매트릭스가 있으면 "이 사분면에 위치해야 한다"를 한 줄 명시.
5. **처음 보는 사람도 이해되는가** : 내부에서만 통하는 비유를 빼고 리터럴하게.

하나라도 아니면 다시 작업한다.

---

## 3. 교재형 카피는 후킹을 뺀다

강의 목차·교안·교재 챕터 제목은 마케팅 카피가 아니라 설명형으로 쓴다.

- 안 됨 : "공포 극복", "AI를 손발처럼" (썸네일·광고 카피 패턴)
- 됨 : "여러 AI를 한 번에 부리는 법", "AI가 거짓말 못 하게 하는 법"

판단 기준은 하나다. 읽는 사람이 목차만 보고 "여기서 뭘 배우나"를 바로 아는가.
모르면 후킹을 빼고 전문용어를 푼다.

적용 범위는 교재형 자료뿐이다. 영상 제목·썸네일·광고 카피에는 후킹을 그대로 쓴다.

---

## 4. 표준 워크플로우

### Step 1. 자료 확인

받은 자료를 먼저 전부 찾는다. 기억에 있는 목록을 사실로 쓰지 않는다.
브리프가 여러 경로(폴더·문서 저장소·메일 첨부)로 흩어져 있을 수 있으니,
"자료가 없다"는 말은 접근 가능한 곳을 전부 확인한 뒤에만 한다.

### Step 2. 검수 기준 소스 확정

작업을 시작하기 전에 "무엇을 기준으로 쓰나"를 먼저 확정한다.

- 최초 제작이면 브리프
- 피드백을 받은 뒤라면 그 피드백 자료가 기준이다. 예전 브리프가 아니다.

불분명하면 물어본다. 기준을 잘못 잡으면 작업 전체가 엉뚱한 방향으로 간다.

### Step 3. 브리프 정독과 핵심 자산 발굴

요약하지 말고 이 고객사만의 무기를 찾는다.
키워드 5개 / 금기어 / 톤 원칙 / 차별점 / 페인포인트 / End Benefit을 뽑는다.

### Step 4. End Benefit 사다리

```
Feature   : 무엇을 하는가
Function  : 어떻게 작동하는가
Benefit   : 무엇이 좋아지는가
End Benefit : 결국 고객의 인생에서 무엇이 바뀌는가
```

B2B와 B2C가 둘 다 있으면 사다리도 두 축으로 나눈다.

### Step 5. 작성 우선순위

1. **브리프 기반** : 모든 슬로건·매니페스토는 브리프에서 나온다.
2. **글쓰기 원칙** : 이 문서 1~3장 + `brandlogy_lint` ERROR 0.
3. **좋은 문장 참고** : 평소 모아둔 문장 아카이브를 훑어 더 좋은 구조·단어가 있으면 빌린다.
   그대로 베끼지 않고 구조·리듬만 흡수한다. 결이 안 맞으면 안 빌려도 된다.

순서가 핵심이다. 참고 문장을 1순위로 끌어와 브리프를 덮지 않는다.

### Step 6. 카피 풀패키지

- **슬로건** 5~7 카테고리, 각 3~5개. 브리프 자산 하나당 카테고리 하나.
- **매니페스토** 5~7안. 안마다 시작 문장이 완전히 달라야 한다.
  결을 분기한다(본질·역사·인물·차별점·고객 페인·시간·비유).
  한 안은 짧은 산문 5~12줄, 마지막 줄에 브랜드명 단독.
- **영업·결제 자극 카피** : 모든 문장이 "그래서 고객한테 뭐가 좋은데"에 답해야 한다.
  결정권자용과 최종 고객용을 분리한다.
- **명함 문구 / SNS 바이오 / 공간 카피 / 보도자료 헤드라인** : 필요할 때.

**각 안에 "왜 이렇게 썼는지"를 함께 남긴다.** 어떤 브리프 자산·어떤 차별점에서 나왔는지
한 줄이면 된다. 카피는 결과물만 넘기면 받는 사람이 판단도 수정도 못 한다.

### Step 7. 1인칭 문장에는 원문을 병기한다

**대표·원장 등 고객사 인물이 '나'로 말하는 문장에 들어간 구체적 수치·빈도·행동은,
쓰는 그 자리에서 브리프·미팅록 원문 인용을 옆에 병기한다.
병기할 원문이 없으면 그 문장은 애초에 쓰지 않는다.**

사후 검수가 아니라 작성 자체를 막는 규칙이다. 지어낸 1인칭 문장은 문법적으로 완벽하고
읽기도 좋아서 린트가 절대 못 잡는다. 브리프 원문과 손으로 대조해야만 걸린다.

작성 중에 이렇게 자문한다.

| 쓰려는 것 | 확인 |
|---|---|
| 숫자 (횟수·기간·주기·연차) | 브리프나 미팅록에 그 숫자가 있나 |
| 습관·행동 ("~합니다", "~하곤 합니다") | 고객사가 실제로 그렇게 말했나 |
| 감정·동기 ("저는 ~라고 생각합니다") | 발화 근거가 있나, 내가 지어낸 캐릭터인가 |

셋 중 하나라도 근거가 없으면 지운다. 남기고 싶으면 고객사에 "이런 사실이 맞습니까"를
확인받은 뒤에 넣는다.

**매니페스토는 창작이지만 사실은 창작 대상이 아니다.** 구조·리듬·비유는 만들어도 되고,
고객사의 이력·습관·수치는 만들면 안 된다. 업종에 따라서는 광고 규제 문제까지 겹친다.

### Step 8. 제출 전 자체 검증

- [ ] 입말 : 말하는 사람이 평소 안 쓰는 단어가 섞이지 않았나
- [ ] 금기어 : 브리프가 명시한 금기어가 들어가지 않았나
- [ ] End Benefit : 모든 안이 End Benefit에 닿았나
- [ ] 브리프 충실도 : 핵심 컨셉과 각 안이 정합한가
- [ ] 카피워싱 다섯 질문 통과
- [ ] 브리프 전수 대조 : 요청받지 않아도 스스로 키워드·금기어·톤·필수 요소를 전부 대조해
      빠진 것을 보강했나. 이 대조 없이 제출하면 미완성이다.

## 5. 같은 카피가 여러 곳에 있으면 전부 맞춘다

카피 한 건은 대개 여러 곳에 동시에 존재한다. 원고 파일, 공유 문서, 회신 초안.
한 곳만 고치고 "수정 완료"라고 하면 나머지가 구버전으로 남는다.
검수자가 여럿 붙은 건일수록 위험하다. 각자 자기가 본 곳만 고치기 때문이다.

수정한 뒤 이 순서로 확인한다.

1. 고친 문장 중 가장 특징적인 5~10개를 뽑아 검사 목록을 만든다
2. 사본이 있는 곳 전부에 그 문구를 검색한다
3. **구버전 잔존 0** 과 **신버전 존재** 를 둘 다 확인한다. 한쪽만 보면 놓친다
4. 불일치가 나오면 정본을 먼저 정하고(대개 가장 최근 검수를 받은 쪽) 나머지를 맞춘다

```bash
# 예시: 원고 파일에 구버전이 남았는지
for k in "구문장1" "구문장2"; do grep -q "$k" "$FILE" && echo "[남음] $k"; done
```

**낭독 모호성은 게이트가 다 못 잡는다.** 한 글자 명사(이·눈·배·말)가 조사와 붙어 다른
뜻으로 들리는 자리가 있다. 소리 내어 읽어서 확인한다. 특히 문서 맨 앞 문단.

## 6. 검토 회신 쓸 때

검토 결과를 회신할 때는 `review_reply_lint.py`를 쓴다.
회신에서 잘 썼다고 칭찬한 원문은 수정본에서 그대로 살아 있어야 한다.
칭찬해 놓고 그 문장을 고쳐 보내면 받는 사람이 회신과 첨부를 대조하다 신뢰를 잃는다.

---

## 7. 코드 게이트 (예외 없음)

카피를 쓰면 반드시 검사한다.

```bash
python3 scripts/brandlogy_lint.py 카피.txt
echo "카피 한 줄" | python3 scripts/brandlogy_lint.py -
```

**ERROR 0을 확인한 뒤에만** 납품·빌드·회신·업로드를 한다.
줄표(— –), 이모지, "솔직히" 류, 대조말투가 ERROR로 잡히면 그 카피로 진행하지 않는다.
0으로 고쳐 통과시킨 뒤 진행한다. 통과 전에 "완료"라고 하면 거짓 완료다.

코드가 못 잡는 것(보이스, 비유 없이 한 번에 이해되는지, So what, 입말)은
이 문서 1~4장으로 직접 본다.

## 8. 자주 하는 실수

| 실수 | 교정 |
|---|---|
| 자료를 한 곳만 보고 "없습니다" | 접근 가능한 곳을 전부 확인한 뒤에만 없다고 말한다 |
| 단어 몇 개 다듬고 검토 완료 보고 | 새 글 수준으로 다시 쓴다 |
| 매니페스토에 결이 같은 안이 둘 이상 | 시작 문장부터 결을 분기한다 |
| 참고 문장을 그대로 베낌 | 구조·리듬만 흡수한다 |
| 브리프 금기어 사용 | 제출 전 금기어 대조를 자동으로 돈다 |
| 기존 기록을 덮어씀 | 누적이 원칙이다 |
| 진단만 길게 하고 끝냄 | 다음 한 수를 준다 |

---

## 9. 작업 끝나고 보고할 때

1. 결과물 위치 (최상단)
2. 작업 요약 : 카테고리·안 개수만 한 줄씩
3. 핵심 자산 : 검증된 것만, 출처를 밝혀서
4. 금기어 검증 통과 : 어느 금기어를 어떻게 피했는지
5. 다음 액션 한 줄

본문을 너무 자세히 풀지 않는다. 결과물을 직접 보면 되는 내용이다.
